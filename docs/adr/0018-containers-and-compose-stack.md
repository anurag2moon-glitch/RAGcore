# 0018: Containers (multi-stage Dockerfile) and the Compose stack

## Status

Accepted.

## Context

ADR 0014 laid out the container topology (api/worker/migrate/postgres/
redis/minio) without specifying how the images themselves get built.
This ADR covers that, plus the liveness/readiness design the images'
own `HEALTHCHECK` directives depend on, plus the Compose stack that
wires everything into one `docker compose up`.

No Docker daemon is available in this development environment (the
same constraint already noted in ADR 0005/0016 for Postgres) - every
Dockerfile/Compose decision below is verified as far as is possible
without a real `docker build`/`docker compose up`: the exact `pip
install` sequence the builder stage runs, and every `COPY` source
path, were run and confirmed for real in a throwaway venv (see the
commit this ADR ships with); the Compose YAML was parsed and schema-
checked; the image build itself was not.

## Decisions

**Liveness vs. readiness, two different checks.** `GET /health` and
`/health/live` are pure liveness - no I/O, always `200` once the
process is up - because a liveness probe answering anything other than
"is this process alive" risks an orchestrator restarting a perfectly
healthy process over a transient dependency outage. `GET /health/ready`
(app/readiness.py) actually reaches whichever of Postgres/Redis/the
corpus's vector store this deployment configured, via a *fresh*
connection per check (never a cached singleton - a connection cached
healthy before an outage would otherwise report healthy forever). An
unconfigured dependency is absent from the report, never counted as a
failure, so a minimal deployment with nothing configured is trivially
ready.

**One Dockerfile, three `--target` stages (api/worker/migrate), not
three Dockerfiles.** They share 100% of the dependency-install and
code-copy layers and differ only in `CMD`/`HEALTHCHECK` - three
separate files would drift the moment one got a dependency bump the
others didn't.

**Build context is the repo root, not `server/`.** `ragcore/` lives
at the repo root as `server/`'s sibling package (ADR 0008); the image
needs both, so the Dockerfile (at `server/Dockerfile`) is built with
`-f server/Dockerfile .` - confirmed every `COPY` source path in it
resolves from the repo root.

**Pinned dependencies via a committed lockfile
(`server/requirements.lock.txt`), not pyproject.toml's `>=` floors.**
"Pinned dependencies" was an explicit requirement. pyproject.toml's
specifiers are deliberately loose (a library consumer's own floor);
the Docker image installs this lockfile's exact versions instead, for
a reproducible build. The lockfile is a plain `pip freeze` of a clean
venv with only `ragcore`+`ragcore-server`'s production dependencies
installed (no dev/test tooling - pytest/moto/fakeredis/httpx never
reach the image), regenerated by hand per its own header comment.
`ragcore`/`ragcore-server` themselves install with `--no-deps`
immediately after, since the lockfile already satisfies everything
they need (verified: `from app.main import app` succeeds from exactly
this install sequence in a scratch venv).

**Non-root user (`appuser`, uid 1000), small final image.** The
`runtime` stage installs nothing itself - it only copies
`site-packages`/`bin` from the `builder` stage - so no compiler
toolchain, no `pip` cache, no source tree beyond `app/`/`alembic/`/
`scripts/` ends up in the final image layers.

**Worker healthcheck via a PID file + `kill -0`, not `pgrep`.**
`python:3.12-slim` doesn't ship `procps` (no `pgrep`), and installing
it just for a healthcheck is an avoidable extra package. `rq worker
--pid /tmp/rq_worker.pid` writes a pidfile; `kill -0 $(cat pidfile)`
(POSIX: checks a process exists, sends nothing) needs only a shell
built-in.

**Graceful worker shutdown needs no code at all.** `rq.worker.Worker
.request_stop` (confirmed via source inspection, ADR 0017) already
finishes the in-flight job on the first `SIGTERM` and only force-exits
on a second - exactly Docker Compose's own default stop sequence
(`SIGTERM`, then `SIGKILL` after `stop_grace_period`).

**MinIO needs an explicit bucket-creation step.** Unlike S3 itself,
a fresh MinIO container has no buckets - a one-shot `minio-init`
service (the official `minio/mc` image) runs `mc mb --ignore-existing`
once MinIO reports healthy, before `api`/`worker` start.

**Migration is a one-shot Compose service (`migrate`), gated with
`depends_on: condition: service_completed_successfully`** - `api`/
`worker` only start after it exits 0, satisfying "run automatically
on startup via a one-shot migration container" without either
long-running service racing the schema.

**`OTEL_EXPORTER_OTLP_ENDPOINT` points at the Compose network's
`otel-collector` service**, not `localhost` - see ADR 0019 for the
tracing/metrics/logging design itself.

## Consequences

- `server/requirements.lock.txt` needs manual regeneration (its own
  header documents the exact steps) whenever `pyproject.toml`'s
  dependencies change - a process gap worth automating in CI later
  (e.g. a CI job that fails if the lockfile is stale), not solved here.
- The image build itself remains unverified end-to-end (no Docker in
  this environment) - the CI pipeline's own "build images" step
  (section 5 of the deployment task) is the first point this actually
  gets built for real, and should be treated as the first true
  verification of this Dockerfile.
- No Kubernetes/autoscaling this pass, per the task's own rule -
  `docker compose`'s `restart: unless-stopped` is the full extent of
  this stack's self-healing. A future ADR should cover a Kubernetes
  migration if/when staging needs to become multi-node.
